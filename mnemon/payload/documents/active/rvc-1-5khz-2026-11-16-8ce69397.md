# 正太音模拟器：自训男童 RVC + 高频搁架，端到端验收记录（2026-11-16）

项目目录：`/Users/liuyongze/Documents/正太音`。本文是前置文档 2c621ccf-ebba-47c4-9913-1c9f3f8b4e7c（RVCMAX 全部 <85 分 → 必须自训、打分口径、ChildTalk 语料选型）的**执行结果**：训练跑完、模型进 app、端到端导出并通过 measure_voice 验收。

## 1. 结论

- 默认音色已切到自训男童模型 `shotaboys`，app 内「导入 → 效果 → 导出 WAV」的端到端产物打分 **100 PASS**（F0 中位 252.8 Hz、p10 213.8 Hz、谱质心 1373 Hz、浊音 65.1%）。
- **模型不是唯一瓶颈，高频泛音缺失才是"闷"的主因**：1.5 kHz +6 dB 高频搁架是决定性改动；模型的作用主要是把 F0 与浊音占比拉回正常区间。
- 证据形态：旧默认 11 分 FAIL（F0 p10 100 Hz、质心 467 Hz）→ 新链路 100 分 PASS（p10 约 207–214 Hz、质心 1232–1373 Hz）。

## 2. 训练发现（关键机制，可直接复用）

1. 默认微调只解冻说话人向量 `emb_g`，**几乎完全不动音色**：step-000 → step-100 的谱质心仅 531 → 534 Hz，等于白训。
2. 加上 `--speaker-cond`（解冻条件层）后才出现真实变化：step-030 谱质心 781 Hz；同时修掉 F0 掉到约 100 Hz 的老毛病（p10 99.7 → 207.7）。
   - 教训：对 MLX RVC 做音色微调时，"只解冻 emb_g"是无效操作，必须解冻 speaker conditioning 层；否则会误判为「数据不够」。
3. 训练数据只用 ChildTalk 的 368 条 / 30 分钟 / 136 场对话（真实男童 4–8 岁）。

## 3. 后级处理（已固化进仓库）

- `script/rvc_worker.py` 内固定 1.5 kHz +6 dB 高频搁架，**文件模式与实时 stream 模式共用同一实现**；实时链路保留滤波器状态，峰值超过 0.99 才软限幅。
- 于是 app 导出与命令行渲染走同一条链，指标几乎一致（质心 1235 vs 1373），可把 CLI 渲染当 app 行为的代理来调参。

## 6. 必踩坑：macOS「文稿」授权导致"RVC 变声超时"

- 现象：app 点「效果」报超时。`Sources/VoiceAudio/RVCBackend.swift:130` 的 `DispatchSemaphore` 等 180 s 后 terminate，抛 `RVCIssue.timedOut`（文案见同文件 224 行「RVC 等待超时。请重试，或切换到基础变声。」）。
- 根因不是代码：模型/资产在 `~/Documents/正太音/.build` 下，macOS 弹「想访问你的文稿文件夹」授权框无人点击，worker 的 CPython **在启动阶段**就卡死。
- 栈证据（`sample` 873/873 个样本全落在同一处）：`Py_InitializeFromConfig → init_interp_main → _PyConfig_InitPathConfig → PyEval_EvalCode → ... → getpath_readlines → _Py_wfopen → open$NOCANCEL → __open_nocancel`，进程 STAT S、%CPU 0.0。
- 处理：点掉 UserNotificationCenter 窗口的「允许」按钮，效果播放与导出即恢复正常（已触发过 TCC 授权）。
- **复发条件：重新构建或更换签名后可能再次弹框**，且 UI 只会显示"超时"，看不出是权限问题。
- 排查捷径：
  - `ps` 看 worker 是否 0% CPU 卡住；`sample` 看是否停在 `__open_nocancel`。
  - 手动跑 worker 会因缺 PYTHONPATH 报 `ModuleNotFoundError: No module named 'rvc_mlx'`——`rvc_mlx` 位于 `.build/rvc/runtime/rvc_mlx`（`script/build_and_run.sh:56` 用 `-d "$rvc/runtime/rvc_mlx"` 做存在性检查），必须把该 runtime 放进 `PYTHONPATH` 且设 `PYTHONNOUSERSITE=1`。
  - app 侧把 worker 的 stdin/stdout/stderr 全接到 `/dev/null`（fd 0/1/2 → `/dev/null`，见 `RVCBackend.swift` 的 `standardError = FileHandle.nullDevice`），所以看不到 traceback，只能靠 `sample` / 手动复现。
